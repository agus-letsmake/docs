## Overview

This endpoint is designed for CI/CD pipelines to push automated test results. It can either create a new execution or update an existing one, and automatically generates step results based on the overall test status.

## Use Cases

## Request Body

<ParamField body="executionId" type="string">
  Existing execution ID to update (mutually exclusive with `suiteId`)
</ParamField>

<ParamField body="suiteId" type="string">
  Suite ID to create new execution for (mutually exclusive with `executionId`)
</ParamField>

<ParamField body="suiteName" type="string">
  Suite name (automatically fetched if not provided)
</ParamField>

<ParamField body="name" type="string">
  Name for the new execution (e.g., "CI Run - Sprint 5")
</ParamField>

<ParamField body="version" type="string">
  Build or release version being tested
</ParamField>

<ParamField body="environment" type="string">
  Environment name (e.g., "staging", "production", "ci")
</ParamField>

<ParamField body="autoComplete" type="boolean" default={false}>
  Automatically mark execution as completed when all tests are processed
</ParamField>

<ParamField body="results" type="array" required>
  Array of test results to push

    <ParamField body="testCaseId" type="string" required>
      ID of the test case (must exist in the system)
    </ParamField>
    <ParamField body="status" type="string" required>
      Test result status. One of: `pass`, `fail`, `skipped`, `blocked`
    </ParamField>
    <ParamField body="duration" type="integer">
      Test execution duration in milliseconds
    </ParamField>
    <ParamField body="errorMessage" type="string">
      Error message or stack trace for failed tests
    </ParamField>
    <ParamField body="notes" type="string">
      Additional notes about the test execution
    </ParamField>
  </Expandable>
</ParamField>

## How It Works

### Step Result Auto-Generation

The endpoint automatically generates step results based on the overall test status:

- **Pass**: All steps are marked as `pass`
- **Fail**: All steps are marked as `fail`
- **Skipped**: All steps are marked as `skipped`

This eliminates the need to manually track step-by-step results in automated tests.

### Creating vs. Updating

**Create New Execution:**
```json
{
  "suiteId": "suite-123",
  "name": "CI Run - Build #456",
  "version": "v1.2.3",
  "environment": "staging",
  "results": [...]
}
```

**Update Existing Execution:**
```json
{
  "executionId": "exec-789",
  "results": [...]
}
```

### Test Case ID Mapping

Your automated tests need to reference TestLab test case IDs. We recommend:

1. **Naming Convention**: Include the test case ID in your test name
   ```javascript
   test('tc-001-login-valid: User can login with valid credentials', ...)
   ```

2. **Mapping File**: Maintain a mapping between test names and IDs
   ```javascript
   const testMapping = {
     'login with valid credentials': 'tc-001-login-valid',
     'login with invalid credentials': 'tc-002-login-invalid'
   }
   ```

See our [Jest Integration Guide](/guides/ci-cd-integration) for a complete example.

```javascript JavaScript/Node.js
const response = await fetch('https://testlab.letsmake.com/api/automated-results', {
  method: 'POST',
  headers: {
    'X-API-Key': process.env.TESTLAB_API_KEY,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({
    suiteId: 'suite-123',
    name: `CI Run - Build #${process.env.BUILD_NUMBER}`,
    version: process.env.VERSION,
    environment: 'ci',
    autoComplete: true,
    results: [
      {
        testCaseId: 'tc-001-login-valid',
        status: 'pass',
        duration: 234
      }
    ]
  })
});

const data = await response.json();
console.log(`Execution ID: ${data.executionId}`);
console.log(`Pass: ${data.summary.pass}, Fail: ${data.summary.fail}`);
```

```python Python
import requests
import os

url = "https://testlab.letsmake.com/api/automated-results"
headers = {
    "X-API-Key": os.environ["TESTLAB_API_KEY"],
    "Content-Type": "application/json"
}
payload = {
    "suiteId": "suite-123",
    "name": f"CI Run - Build #{os.environ['BUILD_NUMBER']}",
    "version": os.environ["VERSION"],
    "environment": "ci",
    "autoComplete": True,
    "results": [
        {
            "testCaseId": "tc-001-login-valid",
            "status": "pass",
            "duration": 234
        }
    ]
}

response = requests.post(url, json=payload, headers=headers)
data = response.json()
print(f"Execution ID: {data['executionId']}")
print(f"Pass: {data['summary']['pass']}, Fail: {data['summary']['fail']}")
```

## Best Practices

<AccordionGroup>
  <Accordion title="Use Environment Variables">
    Store your API key in environment variables, never in code:
    ```bash
    export TESTLAB_API_KEY=tlk_your_api_key_here
    export TESTLAB_SUITE_ID=suite-123
    ```
  </Accordion>

  <Accordion title="Include Build Information">
    Add version and environment information to track results over time:
    ```json
    {
      "version": "v1.2.3",
      "environment": "staging",
      "name": "CI Run - Build #456"
    }
    ```
  </Accordion>

  <Accordion title="Use Auto-Complete">
    Set `autoComplete: true` to automatically mark executions as done:
    ```json
    {
      "autoComplete": true
    }
    ```
  </Accordion>

  <Accordion title="Include Error Details">
    For failed tests, include stack traces for easier debugging:
    ```json
    {
      "status": "fail",
      "errorMessage": "Expected value to be true\n    at test.js:42:10"
    }
    ```
  </Accordion>

  <Accordion title="Track Duration">
    Include test duration for performance monitoring:
    ```json
    {
      "duration": 1234
    }
    ```
  </Accordion>
</AccordionGroup>
