---
title: "Push Automated Results"
api: "POST /api/automated-results"
description: "Push results onto an open automated execution"
---

Prefer the [Playwright SDK](/docs/cli-sdk/playwright) or
[Client `pushResults`](/docs/cli-sdk/client). This page is the HTTP contract
those packages call.

## Recommended flow

1. `POST /api/automated-results/start` → `executionId` (seeds suite `todo` rows)
2. `POST /api/automated-results` with that `executionId` and `results[]`
3. Cleanup: `completeExecution` / reconcile (or `autoComplete: true` when
   `todo` is already zero)

Do **not** create a new execution on every result batch in CI. Start once per
job.

## Authentication

<ParamField header="X-API-Key" type="string" required>
  Project-scoped API key
</ParamField>

<ParamField header="X-Project-Id" type="string" required>
  Project id or slug
</ParamField>

## Request body

<ParamField body="executionId" type="string" required>
  Execution from `/start`. (Creating via `suiteId` on this endpoint is legacy;
  new runners should start first.)
</ParamField>

<ParamField body="autoComplete" type="boolean" default={false}>
  Ask the API to complete after this push. Succeeds only when suite `todo` is
  zero. CI usually sets `TESTLAB_DEFER_COMPLETE=1` and completes in cleanup
  instead.
</ParamField>

<ParamField body="results" type="array" required>
  Array of results
  <Expandable title="Result properties">
    <ParamField body="automationKey" type="string" required>
      Catalog key (preferred). Must match an imported case.
    </ParamField>
    <ParamField body="status" type="string" required>
      `pass`, `fail`, `skipped`, or `blocked`
    </ParamField>
    <ParamField body="duration" type="integer">
      Duration in milliseconds
    </ParamField>
    <ParamField body="errorMessage" type="string">
      Failure detail (Client redacts secrets before send)
    </ParamField>
    <ParamField body="runnerEmail" type="string">
      Account used for this attempt
    </ParamField>
    <ParamField body="runnerPersonaKey" type="string">
      Optional persona / fixture key
    </ParamField>
    <ParamField body="attachments" type="array">
      Previously uploaded attachment objects (second push after
      `uploadAttachment`)
    </ParamField>
  </Expandable>
</ParamField>

<RequestExample>
```bash Push onto an open execution
curl -X POST https://testlab.letsmake.com/api/automated-results \
  -H "X-API-Key: tlk_your_api_key_here" \
  -H "X-Project-Id: your-project-id" \
  -H "Content-Type: application/json" \
  -d '{
    "executionId": "exec-789",
    "results": [
      {
        "automationKey": "DEMO-01",
        "status": "pass",
        "duration": 234,
        "runnerEmail": "runner@example.com"
      },
      {
        "automationKey": "DEMO-02",
        "status": "fail",
        "duration": 890,
        "errorMessage": "Expected heading to be visible"
      }
    ]
  }'
```
</RequestExample>

## Mapping tests to cases

Put the automation key in the Playwright **tag or title** (or pass
`resolveAutomationKey`). Import those keys via a
[Portable Catalog](/docs/concepts/portable-catalog) before CI runs.

Legacy `testCaseId` mapping files are only for runners that cannot send
`automationKey` (for example some JUnit converters). New work should use keys.
